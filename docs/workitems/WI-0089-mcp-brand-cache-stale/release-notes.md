# WI-0089: MCP 브랜드 도구의 tokens 판독 낡음 릴리스 노트

> **발행**(2026-10-30, npm cli 1.7.8 · mcp 1.4.7, Version PR #259 · publish run 41062612171, provenance 2/2). 아래는 2026-10-29 작성). 반박 검증 보정 뒤 최종본 측정 반영([testplan 4절](./testplan.md)). 사용자 결정 Q80 ~ Q85 는 모두 권장안이에요([prd 1.4](./prd.md)). 진행 중 생긴 결정 후보 Q86 · Q87 은 권장안대로 구현해 두었고 확인을 기다려요([prd 6절](./prd.md))
> 대상: `@axis-ds/cli` patch · `@axis-ds/mcp` patch(`.changeset/wi-0089-mcp-brand-cache-stale.md`) | GitHub: #224

## 바뀐 점

- MCP `axis.list_brands` · `axis.get_brand` 는 같은 서버 세션 안에서 대상 프로젝트의 `@axis-ds/tokens` 가 바뀌면 다음 호출부터 새 상태로 판정해요. 서버를 다시 시작할 필요가 없어요. 지금까지는 그 세션에서 처음 읽은 package.json 의 `exports` 로 계속 판정했어요(Node 가 처음 읽은 package.json 을 프로세스가 끝날 때까지 기억하기 때문). 고친 예:
  - 1.2.1 에서 1.7.0 이상으로 올렸는데 「`@axis-ds/tokens 1.8.2 은 브랜드를 지원하지 않습니다`」가 나오던 경우(버전만 새 값). 이제 정상 목록 · 상세예요
  - 1.8.2 에서 1.2.1 로 내렸는데 「빌드 산출물이 없어」가 나오던 경우. 이제 「브랜드를 지원하지 않습니다」예요
  - tokens 를 지웠다 다시 설치해도 풀리지 않던 경우
  - 같은 버전에 브랜드를 더했는데 도구가 `Package subpath './brands/<이름>/brand.json' is not defined by "exports"` 오류로 끝나던 경우. 이제 새 브랜드가 목록에 들고 상세를 읽어요
  - 모노레포에서 앱 안의 중첩 tokens 를 지워 상위 설치본으로 넘어간 경우. 상위 설치본으로 판정해요
- 고친 방식: 세션 안에서 tokens package.json 의 내용(sha256, 패키지를 찾는 동안 본 후보 경로의 「없음」 포함)이 처음 해석했을 때와 다르면 그 호출의 해석을 Worker 스레드에서 해요(사용자 결정 Q80 · Q81). 내용이 같으면 종전과 같은 해석이에요. 설치 도중에 불려 기록과 실제 판독이 어긋날 수 있으면 그 경로는 그 뒤로 Worker 로 해석해요.
- Worker 를 띄우지 못하거나 응답이 없으면(5 초) 종전처럼 판정하고 응답 끝에 한 줄을 붙여요(사용자 결정 Q83): 「- 주의: 이 MCP 서버가 @axis-ds/tokens 를 처음 읽은 뒤 내용이 바뀌었는데 새 상태를 다시 읽지 못했습니다. 위 결과는 이전 설치 기준일 수 있으니 MCP 서버를 다시 시작하세요.」 그 뒤로 그 세션에서는 Worker 를 다시 띄우지 않아요. 이때 종전 판정으로는 읽을 수 없는 새 브랜드는 목록에서 빠지고 상세는 「없는 이름」으로 보여요(도구 오류로 끝나지 않음).

## 비용

- tokens 가 바뀌지 않은 호출은 종전과 같아요(측정: 호출 왕복 중앙값 약 1 ~ 2 ms, 발행본과 번갈아 잰 차이가 잡음 안).
- tokens 가 바뀐 뒤에는 그 서버 세션이 끝날 때까지 브랜드 호출마다 Worker 하나를 띄우는 만큼 더 걸려요(측정: 이 머신 Node 22 에서 약 25 ~ 29 ms). 버전 문자열만 바뀐 경우도 같아요. 서버를 다시 시작하면 다시 종전 비용이에요.

## 바뀌지 않은 점

- `axis theme list` · `axis theme info` · `axis theme add` 의 출력 · 종료 코드 · 쓰는 파일은 바이트 단위로 같아요(측정: 발행본 cli 1.7.7 과 30쌍 대조). CLI 는 명령마다 새 프로세스라 늘 처음 해석이에요. CLI 와 MCP 가 같은 브랜드 코어(바이트 사본)를 써서 두 패키지를 함께 올려요(사용자 결정 Q84).
- `axis.check_project` 는 파일을 직접 읽어 원래 세션 안의 변경을 따라갔고(착수 측정), 이번에도 바뀌지 않아요(측정: 172칸 하네스에서 응답 바이트 같음). 그 밖의 MCP 도구는 이 해석을 쓰지 않아요(코드 조사).
- 미설치 · 미지원 · 빌드 전 · 정상의 판정 규칙과 안내 문구는 그대로예요. 새로 붙는 것은 위 폴백 한 줄뿐이에요.

## 측정 요약

- 한 프로세스 하네스(13 시퀀스 · 172칸): 같은 프로세스와 새 프로세스의 응답이 갈리는 칸이 발행본 20 → 최종본 0. 새 프로세스 응답은 172칸 모두 발행본과 바이트 같아요. Node 22.22.0 · 24.18.0 에서 같은 결과예요.
- 새 테스트 cli 13 · mcp 3 건은 main 소스에서 모두 빨강이고 최종본에서 초록이에요. 변이 12개도 모두 빨강(또는 처리되지 않은 오류로 실행 실패)이었어요.
- 독립 반박 검증에서 결함 2건(중첩 설치본 제거 · 폴백 중 브랜드 추가)과 위험 3건(경합 · Worker 오류 처리 · 실패 반복 대기)을 찾아 고쳤고, 같은 재현으로 새 프로세스와 같아짐을 확인했어요(testplan 4.9).

## 잔여 · 알려진 한계

- Node 20 에서는 재지 않았어요(이 머신에 없음). 같은 방식으로 package.json 을 기억해 같은 결함이 있고, 이 수정으로 같이 풀릴 것으로 추정해요.
- Yarn Plug'n'Play 레이아웃에서는 재지 않았어요.
- 바뀐 뒤 호출마다 Worker 를 새로 띄워요. 결과를 기억해 두지 않는 것은 새 캐시와 그 무효화를 다시 만들지 않기 위해서예요(결정 Q86, 권장안대로 구현하고 2026-10-30 확정).
